## Goal
Add a Blockly statement block to set a pib 3-LED button's color from a Colour VARIABLE, with the color variable
on the RIGHT-HAND side of the block (unlike the existing tf_button_set_color which uses a fixed inline colour field).

## Verified existing pattern (this repo)
- `program-blocks/tf-button-block.ts`:
  - `tf_button_set_color` = message0 "button %1 set color %2", BUTTON_ID dropdown (1/2/3), then a `field_colour`
    named COLOR (fixed). previousStatement/nextStatement null.
  - `tf_button_taster_to_variable` uses a `field_variable` (name VAR).
- `program-generators/tf-button-generator.ts`:
  - `tf_button_set_color` reads BUTTON_ID + fixed COLOR (field_colour) -> hexToRgb -> emits
    `blockly_client.set_button_color(<id>, r, g, b)`.
  - `hexToRgb(hex)` helper exists; `configureGenerator(generator)` wires IMPORT_* / INIT_*.

## Desired new block (add, do not change existing)
Add a new statement block (e.g. type `tf_button_set_color_from_var`):
- message0: "button %1 set color from variable %2"   (color variable on the RIGHT-hand side)
- BUTTON_ID dropdown 1/2/3 (same as existing).
- The color comes from an INPUT that accepts a Blockly Colour VARIABLE (right-hand side). In blockly terms this is
  either a `field_variable` typed to colours, or — better — a value-input `input_value` named COLOR that accepts a
  colour variable / colour expression block. Use the colour variable approach so a stored colour variable can be
  applied at runtime.
- previousStatement/nextStatement null, colour ~20, tooltip explaining it sets the RGB LED of the button from a
  colour variable.

Generator: new export function (auto-registered via the spread in custom-generators if you add it there, or add to
the same module's registration; match the block type). It should:
- read BUTTON_ID.
- read the colour from the variable/input (e.g. `generator.valueToCode(block, "COLOR", Order.NONE)` for an
  input_value, OR resolve a field_variable name).
- Emit the same `blockly_client.set_button_color(<id>, <R>, <G>, <B>)` call, where R/G/B come from the variable —
  i.e. the variable holds a colour; derive r/g/b from it at runtime (pass the resolved r/g/b expressions, not a
  static hex). Keep it consistent with the existing runtime function signature.

Do NOT change tf_button_set_color / the existing blocks' behaviour.
